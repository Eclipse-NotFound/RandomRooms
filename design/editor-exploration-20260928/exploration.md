# 编辑器接入探索：先建立可靠的生成结果审查

2026-09-28。阅读 [原报告](../editor-integration-20260928/assessment.md) 后，追加真实编解码实验、当前原生绘图库验证和可查看的规划叠层。范围是探索；正式生成器、release、已安装编辑器和游戏文件均未修改。

**建议采用报告的前两步：完整快照＋规划叠层，再增加修改前后对照。** 它能直接帮助当前房间的空旷、重复摆设、破碎效果和布防问题。手工编辑整个房间后送入探索地图，需要更完整的回放与重新验证机制，暂不作为第一步。

[打开四场景审查样例](index.html)。页面使用四份历史 v13 XML 的原生静态图，可以切换用途/D/V、生成点、防守目标、终端路线和接口；点击生成点查看依据。它不是新的随机生成算法，也没有接入编辑器正式面板。

## 本次补充了哪些证据

### 当前编辑器已经支持实体外观

原报告测试的 EditorTools 为 13,255 B；当前是 17,854 B，SHA256 `80cfa1baafe8ed966b696e8379239eb12180fa194bcfb36365e1630b3d91b64c`。新增了敌人、炮塔、地雷等原生静态实体支持。原报告“这些对象被省略”的结论应保留为当时的版本事实，不再用于概括当前版本。

我从当前绘图源码构建了一份独立审查适配器，只补生成房的运行上下文：明确读取场景、镜像、难度和敌群，并给城市传入 `transpFon`。原生绘图库仍为已安装 NativeScene 的原样副本。每个替换点与输入指纹均记录在 [manifest.json](manifest.json)，已安装组件未改。

四张 1920×1000 PNG 均通过格式、CRC、解压像素长度核对，渲染无警告，输入 XML 未变，`loc.units` 均为空。35 是成功构造的静态模型数量，不是屏幕可见敌人的数量或实际敌群规模。本次下水道有 8 个尸鬼模型 `visible=false`；原生 `UnitZombie.animate` 包含潜伏时隐藏身体的分支，探针未读取其受保护的 AI 状态，不能逐只断言原因。**设计预览应始终保留生成点标记，不能根据画面是否看见身体判断是否生成了敌人。**

叠层来自原始 `rrPlan`，含 75 个生成点、8 个炮塔防守目标及 3 条终端候选路线。镜像按与游戏调试层一致的坐标规则处理。相邻房间从完整原池查找，13 个开放接口对的宽度吻合；这只是接口契约核对，不是通行实测。

### 保存风险已由真实编辑器代码复现

在独立 AIR 应用内加载已安装 `Editor.swf` 的原样副本，调用 `decodeAll → ToolsSnapshot → encodeCurrent → encodeAll`，并触发编辑器自己的选房事件。输出写到研究目录；未调用保存对话框，未写正式地图或用户设置。

| 样本 | 重编码丢失的房间附加属性 | rrPlan | doors | 重新选房后的地形、obj、back、options |
|---|---:|---|---|---|
| 工厂 | 30 | 丢失 | 丢失 | 语义一致 |
| 避难厩 | 30 | 丢失 | 丢失 | 语义一致 |
| 下水道 | 31 | 丢失 | 丢失 | 语义一致 |
| 城市 | 33 | 丢失 | 丢失 | 语义一致 |

四份 `<all>` 的版本与种子也都丢失。obj/back 比较忽略对象顺序、保留所有属性与子节点；不是只比对象数量。这与此前“未改的原版工厂地图另存后内容一致”并不矛盾：本次强制经过当前房间重编码，且房间具有编辑器不了解的扩展数据。

另外，四个单房样本都没有 `(0,0)` 房间。`decodeAll` 自动显示该房时，内部地图坐标仍停在 `(0,0)`；立即取得预览快照也就带了错误坐标。触发房间列表的选房事件后恢复原坐标，但扩展信息仍丢失。此问题限于本次这种载入条件，不能概括为所有选房都会错位。

结论是：**读取成功、图像正确、保存可用，必须分别核对。** 审查工具应直接取完整源 XML 和运行上下文；以后编辑回灌时也不能只把旧 `rrPlan` 粘回来。

### 固定种子尚不足以固定每个像素

两次完整渲染使用相同源 XML、上下文和绘图组件。四张图的文件哈希均不同；四个房间的实体外观记录也都出现朝向或变体变化。原生绘图库仍使用 `Math.random` 选择部分未指定装饰帧及单位变体。

这不表示 RandomRooms 的地形种子失效。它说明“同一张生成房”与“完全相同的视觉快照”是两层确定性。比较噪声/破碎方案时应冻结同一份底图，保留基准图，明确本轮变化范围；后续可单独固定预览外观选择，不能修改游戏全局随机函数来强行对齐。

## 怎样接入才有实际收益

### 第一阶段：只读审查与差异检查

建议保存一个房间包，内含完整 XML、版本与主/局部种子、深度与难度、场景与敌群、地图坐标与镜像、实际邻居及接口、生成器/绘图库指纹。不要从编辑器的简化画布重新拼这些信息，也不要把文件名当作场景来源。

原报告的四个老样本和本次四个新样本均来自历史运行导出；本次没有新增游戏内导出快捷键。正式接入时可复用当前测试驾驶器的 `dumpRuntimePool`，再把导出能力独立出来；区分“初始生成记录”与“玩家打坏墙、开门后的现场”。

一个最小、可用的审查入口应当做到：载入完整房间包；自动应用上述上下文；原画/用途/D/V/生成点/布防分层显示；查看邻房；导出带来源的图片。静态画面只显示防守意图，当前枪口方向仍由游戏内 Shift+F3 查看。

本次独立页面与适配器验证了这条路径可行。还未实现的是正式编辑器按钮、游戏现场导出、批量筛选和问题标注。

### 第二阶段：让编辑器帮助设计规则

对当前破碎感改进，我更推荐编辑器承担“对照和测量”工作：

- **外观草稿**：试摆后墙破洞、瓦砾、老化材质，观察同一处破坏是否在多个视觉层上相互对应。背景洞并不意味着地面能穿过。
- **结构草稿**：尝试一处塌方、断板或岩体侵入，记录事件的方向、尺度、保留的梁台及替代路线。然后归纳为生成参数与规则，让新种子也能产生合理结果。
- **摆设草稿**：用实景调整桌柜灯具的相对关系；提取相对位置、占地、适用用途和场景条件，再交给原有放置检查。这仍保留从零生成建筑的方向。

不应把看着不错的一整间手工房直接当作随机生成进展。编辑器的收益来自降低试错成本，最终变化仍要落实到生成规则。

### 第三阶段：受约束的编辑回放

如果以后需要把手改草稿送进游戏，应绑定原房指纹、版本、种子和坐标，以便确认改的是哪一间。草稿状态与“已重新验证”状态分开。

| 改了什么 | 至少哪些信息需要重查 |
|---|---|
| 后墙装饰或视觉材质 | 所属场景、遮蔽关键提示的情况、视觉效果；先核对确实没有改动实体层 |
| 墙体、楼板、门梯、水渠 | 内部房间分组、全入口往返、邻接口、干路、支撑及新打开的交战空间 |
| 炮塔或终端位置 | 支撑、安装方向、射界、候选接近路与控制范围 |
| 敌人、陷阱、奖励设施 | 区域预算、生态、关联机关、占位与容器原生事件 |

仅仅无损保存 XML 不能完成这些验证。尤其拆墙后，原本分开的两个 D/V 区域可能互相支援，原终端路线也可能暴露；应重新规划或明确标记失效。

回放建议先作为固定条件的开发工具，插在 `RRGrowth` 生成 XML 后、校验及 `newLoc` 前。完整修改器和长期手工房池的维护成本明显更高，且会扩大到保存兼容、增长地图和故障恢复；当前没有足够收益支持先做它们。

## 验证范围与复现

- [results.json](results.json)：真实编辑器重编码、当前静态模型、场景/镜像/难度/敌群断言。
- [validation.json](validation.json)：地形/对象语义核对、PNG 与 22 份来源/正式文件指纹、重复渲染差异。22 份是本实验追踪的输入范围，不是整个游戏目录清点。
- [manifest.json](manifest.json)：全部样本与组件指纹、适配器的精确替换点、相邻接口。
- [page-logic-check.json](page-logic-check.json)：四场景切换、叠层、镜像炮塔坐标、点选与原画开关的最小 DOM 执行。不是浏览器排版验收。
- `first-run/` 保留首轮原始结果；`diagnostic-failure/` 保留补充诊断时读取炮塔不存在字段而失败的记录。修正的是探针，不是编辑器或生成器。

在本机依次运行 `prepare.py`、`run-probe.ps1 -Run`、`build_review.py` 可复现。脚本仅写本目录；AIR 用新的唯一应用 ID，窗口隐藏并自动退出。若组件版本或样本改变，应新建研究目录保留本次证据。PNG 与隔离资源副本沿仓库规则留本机，文本和代码入库。

本轮已查看实际 PNG。浏览器工具对本地 file 协议的安全限制仍在，未绕行，页面尚未经过真实浏览器点击和排版检查。没有重新运行正式生成器、AI/战斗、涉水、跨房通行或终端交互测试；也不据静态渲染耗时推断游戏帧率。
